This report documents the live, certified execution of the complete end-to-end fraud detection pipeline across all three functional engineering layers (**Member 1**, **Member 2**, and **Member 3**), the **Integration Bridge**, and the **FastAPI Containerized Serving Engine**.

- **Ultra-Low Latency:** Median streaming pipeline overhead was **0.83 ms**, and median live FastAPI HTTP scoring latency was **91.65 ms**.

## 3. The Journey of a Transaction (Step-by-Step)

Here is what happens to every transaction as it moves through the entire system:

### Step 0: Raw Dataset Source
- **Origin:** The transaction originates from `IEEE CIS/test_transaction.csv`.
- **Raw Input Example:**
  - `TransactionID`: `3663549`
  - `TransactionDT`: `18403224` (Simulated seconds since start)
  - `TransactionAmt`: `31.95`
  - `ProductCD`: `W`
  - `card1`: `10409`
  - Plus 388 raw numerical $V$-columns, $C$-counts, and $D$-timedeltas.

### Step 1: Member 1 — Kafka Ingestion
- **Responsibility:** Ingest raw events from payment channels into Kafka safely and reliably.
- **Action:** The event is packaged into a Kafka record and pushed to the topic `ieee_cis_transactions`.
- **Key Routing:** Keyed on `CARD-10409` across 6 topic partitions to ensure all transactions for the same card land on the same partition in sequential order.
- **Safety Invariant:** Any label column (`isFraud`) is stripped to prevent data leakage.

### Step 2: Member 2 — Flink Streaming Velocity Processor
- **Responsibility:** Stateful real-time stream aggregation and Complex Event Processing (CEP).
- **Action:** Flink maintains in-memory sliding time windows for each card:
  - **5-minute window:** Counts how many times this card transacted in the last 300 seconds (`count_5m`) and the total dollar amount spent (`amount_5m`).
  - **10-minute window:** Tracks 600-second velocity (`count_10m`, `amount_10m`).
  - **Velocity Ratio:** Compares 5-minute velocity against 10-minute historical average to detect sudden spending bursts.
- **Output:** Emitted to the `fraud-features` Kafka topic.

### Step 3: Integration Bridge
- **Responsibility:** Connect streaming event streams with ML serving cleanly without race conditions.
- **Action:**
  - Holds a watermarked `CorrelationBuffer` that matches the incoming transaction with its corresponding Flink velocity record.
  - Enforces **Temporal Causality**: Future velocity records cannot be attached to past transactions.
  - Assembles the standardized `StreamingTransactionPayload`.

### Step 4: Member 3 — Online Feature Hydration Gate
- **Responsibility:** Hydrate compact stream events with static entity profile data while protecting the model.
- **Action:**
  - Looks up `CARD-10409` in the `EntityProfileStore`.
  - Merges static account attributes (`card2`–`card6`, address postal codes `addr1`, `addr2`, purchaser/recipient email domains).
  - **Hard Hydration Gate:** If an account profile is missing or corrupted, it rejects the transaction immediately (`scoreable=False`, HTTP 422), ensuring the ML model is never invoked on broken inputs.

### Step 5: 406 Canonical Feature Vector Assembly
- **Responsibility:** Guarantee strict contract alignment with the frozen E1 model.
- **Action:**
  - Transforms categorical variables using the certified `preprocessing.joblib`.
  - Orders all 406 features in the exact sequence specified by `serving/models/E1/feature_names.json`.
  - Ensures exactly 406 floating-point values enter the booster.

### Step 6: Certified Frozen E1 LightGBM Model Scoring
- **Responsibility:** Ultra-fast, high-precision fraud scoring.
- **Action:**
  - The C++ LightGBM booster computes the fraud probability (`fraud_probability`, e.g., `0.007875`).
  - Applies the **Frozen Decision Threshold ($0.616521$)**:
    $$\text{Decision} = \begin{cases} \text{FRAUD} & \text{if } \text{fraud\_probability} \ge 0.616521 \\ \text{LEGIT} & \text{if } \text{fraud\_probability} < 0.616521 \end{cases}$$

### Step 7: Live FastAPI Serving Layer
- **Responsibility:** Expose reliable, production-ready REST endpoints inside a Docker container.
- **Action:**
  - Receives the request over HTTP port 8000.
  - Returns a structured JSON response (`HTTP 200 OK`) in under 100 ms:
    ```json
    {
      "transaction_id": "3663549",
      "fraud_probability": 0.007875,
      "decision": "LEGIT",
      "actual_label": "UNKNOWN",
      "preprocessing_time_ms": 1.25,
      "model_prediction_time_ms": 0.42,
      "total_inference_time_ms": 1.67
    }
    ```

### Step 8: Prometheus & Metrics Monitoring
- **Responsibility:** Continuous runtime observability.
- **Action:**
  - Records HTTP request count, latency percentiles ($P_{50}, P_{95}, P_{99}$), and status codes.
  - Exposes telemetry via `GET /metrics`.

## 9. Operations Guide: How to Run the API & View Logs

### Option A: Running via Docker (Recommended / Production)

#### 1. Build the Docker Image
From the project root (`d:\adaptive-upi-fraud-detection`):
```bash
docker build -t adaptive-fraud-serving:v1 -f serving/Dockerfile serving
```

#### 2. Run the Container
```bash
docker run -d --name adaptive-fraud-serving -p 8000:8000 adaptive-fraud-serving:v1
```

#### 3. Verify the Container is Running
```bash
docker ps
```
*Expected output shows container status `Up` on `0.0.0.0:8000->8000/tcp`.*

### Option B: Running Directly with Python (Local Development)

If running directly on host without Docker:
```bash
cd serving
python -m uvicorn api.main:app --host 0.0.0.0 --port 8000
```
